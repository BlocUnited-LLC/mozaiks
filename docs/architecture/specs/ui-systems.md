# UI Systems

Mozaiks has three distinct UI surfaces. They share tokens and primitives, but
they do not share one generic authoring contract.

| Surface | What It Owns | Authoring Contract | Renderer |
| --- | --- | --- | --- |
| Transition UI | Pre-workflow and between-workflow routing choices | `extension_registry.json` `entrypoints[]` + `transitions[]` | `TransitionScreen`, `LauncherScreen`, `ConfirmScreen` |
| App UI | Persistent app pages | `app.json` + `pages/*.yaml` schemas | `SchemaPage` + `PageRenderer` |
| Agent UI tools | Runtime UI inside chat/artifacts | Python UI tool + workflow-local React component | WebSocket events + component registry |

## Transition UI

Transition UI is shell-owned routing UI. It is not workflow-local React and it
is not AppGenerator page output.

Entry example:

```json
{
  "path": "/create",
  "label": "Create App",
  "transition": "app_type_selector"
}
```

Transition declaration example:

```json
{
  "id": "app_type_selector",
  "transition_type": "user_choice_context",
  "ui": { "component": "AppTypeSelector", "mode": "screen" },
  "route_to": "ValueEngine",
  "options": [
    { "id": "new_app", "context_variables": { "app_type": "new" } },
    { "id": "existing_app", "context_variables": { "app_type": "existing" } }
  ]
}
```

Rules:

- Keep transition routing semantic in `extension_registry.json`.
- For branded transition visuals, add file-backed transition components under
  `mozaiks-platform/app/workflows/extended_orchestration/ui/` and export through
  `ui/index.js`.
- Do not use workflow sequence declarations (`workflow_sequences[]`) for entry UI.
- Use `transitions[]` for choice/confirm/silent routing and deterministic context seeds.
- Use `ui.component` to bind to a known shell transition screen.
- Keep copy/images/layout in the React transition component file when the UI is
  product-specific.
- Keep route options semantic (`id`, optional `route_to`, optional `context_variables`).
- Transition components emit `option_id`; the router maps that id to route/context effects.
- Use `workflow_sequences[]` only as runtime workflow sequence metadata for auto-advance and between-workflow transition checkpoints.

## App UI

App UI is the persistent page layer generated by AppGenerator.

```yaml
name: customers
title: Customers
layout: grid
sections:
  - id: customer_table
    title: All Customers
    primitive: DataTable
    config:
      columns:
        - { key: name, label: Name }
        - { key: email, label: Email }
    api_endpoint: /api/modules/customers/list
```

Rules:

- AppGenerator writes `app.json` and `pages/*.yaml`.
- Generated app pages default to schema + primitives, not raw React.
- Page layout, spacing, and shell chrome are runtime-owned.
- Brand alignment comes from `theme_config.json`, shell config, and `asset_manifest.json` media references, not per-page styling hacks.

## Agent UI Tools

Agent UI tools are runtime surfaces pushed by a running workflow. They are the
right place for custom React because the component is tied to a workflow tool
contract.

Python producer:

```python
await emit_ui_surface(
    component="ApprovalCard",
    mode="artifact",
    payload={"title": "Approve this plan"}
)
```

React surface:

```jsx
export function ApprovalCard({ payload, onAction }) {
  return <Card title={payload.title} />
}
```

Rules:

- AgentGenerator owns workflow UI tools.
- Every interactive tool has an explicit Python tool contract.
- React components live under the workflow `ui/` folder and export through `ui/index.js`.
- Components compose shipped primitives and theme tokens.
- Shared bridge helpers live in `chat-ui/src/platform`, not in workflow folders.

## Decision Guide

Use Transition UI when the user is choosing where to go or which context to seed before a workflow starts.

Use App UI when the user is navigating persistent pages in a generated app.

Use Agent UI tools when a running agent needs to show data, collect approval, or
emit an artifact.
