# Admin UI Tiers

Mozaiks admin surfaces come in two tiers with distinct ownership, file contracts,
and use cases. Choosing the wrong tier is a common source of misregistered
components and broken Studio layouts.

---

## Tier 1 — AdminPortal Schema Panels

**What it is:** Panels rendered inside the framework-owned AdminPortal shell at
`/admin`. Panels slot into semantic admin sections (`overview`, `access`,
`billing`, `usage`, `activity`, `operations`, `settings`, `integrations`,
`support`) without owning their own route.

**When to use:** For module-owned operator data surfaces — record tables, summary
metrics, approval queues, activity feeds, and settings forms that belong inside
the standard admin shell.

**Files involved:**

| File | Role |
|---|---|
| `admin/admin_registry.yaml` | Declares page shell stubs: ids, paths, scope, icon, order |
| `modules/{module}/contracts/admin.yaml` | Declares panels that reference those page ids |

**Renderers available in `contracts/admin.yaml`:**

- `renderer: schema` — panel config using the same primitive system as
  `ui/pages/*.yaml` (DataTable, Form, SummaryStrip, etc.)
- `renderer: builtin` — built-in platform panels (`stats`, `users`,
  `subscriptions`)
- `renderer: custom_component` — bounded React customization; component declared
  in module JS stubs and registered through `ui/index.js`

**Generator rule:** This is the default generated admin path. AppGenerator
generates `admin/admin_registry.yaml` via `AdminRegistryAgent`. Module panels
are generated by `ConfigMiddlewareAgent` from module contract build tasks.

**Common mistakes:**

- Do not add `component`, `registry_key`, or `renderer` to
  `admin/admin_registry.yaml` entries. The registry declares page stubs, not
  React route components.
- Do not add admin panel pages to `manifest.pages` or `ui/route_manifest.json`.
  The platform mounts `/admin` automatically.
- Do not use `renderer: custom_component` when `renderer: schema` can express
  the panel — custom components introduce a JS stub dependency.

**Example — `admin/admin_registry.yaml` (page stubs only):**

```yaml
schema_version: mozaiks.admin.registry.v1
pages:
  - id: overview
    label: Overview
    path: /admin
    icon: dashboard
    order: 0
    scope: app
    enabled: true
  - id: operations
    label: Operations
    path: /apps/:appId/operations
    icon: server
    order: 50
    scope: app
    enabled: true
```

**Example — `modules/reports/contracts/admin.yaml` (panels referencing page ids):**

```yaml
schema_version: mozaiks.admin.v2
panels:
  - id: reports.activity
    label: Activity Reports
    page: activity
    renderer: schema
    layout: full-width
    sections:
      - id: activity-table
        primitive: DataTable
        config:
          api_endpoint: /api/modules/reports/list_activity
          columns:
            - key: name
              label: Name
            - key: status
              label: Status
              type: badge
```

## Tier 2 — Custom Operator React Pages

**What it is:** Full-page workspace-studio routes registered in the component
registry. These are standalone React pages — not panels inside AdminPortal.
They own their own route, render the full workspace chrome, and are mounted
independently of the AdminPortal panel system.

**When to use:** For operator surfaces that require a full-page layout, custom
navigation context, or complex interactivity that cannot be expressed through the
Tier 1 panel primitive system. Use sparingly — Tier 1 is the default.

**Files involved (all three required together):**

| File | Role |
|---|---|
| `ui/route_manifest.json` | Declares the full-page route with `component` key |
| `admin/pages/{PageName}.jsx` | React component implementing the page |
| `admin/index.js` | Registers the component by `registry_key` so the runtime mounts it |

**Chrome rule:** Pages in `admin/pages/` MUST use `WorkspaceLayout` or
`AppStudioLayout` from `@mozaiks/chat-ui/workspace`. Never use `PageFrame` —
`PageFrame` is for user-facing pages in `ui/pages/custom/` only. Using
`PageFrame` in an admin page hides the workspace sidebar and breaks the Studio
layout.

**Generator rule:** AppGenerator does not generate Tier 2 operator pages by
default. When a full-page operator surface is explicitly required, declare it
through the bounded `custom_route_bundle` contract — route_manifest entry + page
file + `admin/index.js` registration. Do not create standalone admin route
families or ad hoc React shells.

**Registration contract — all three files must be consistent:**

- `ui/route_manifest.json pages[].component` names the runtime component key
- `admin/pages/{PageName}.jsx` default-exports exactly one component for that key
- `admin/index.js` calls `registerComponent(key, Component)` for that key
- No implicit file discovery or admin-registry fallback may substitute for the
  three files above

**Example — `ui/route_manifest.json` (route declaration):**

```json
{
  "pages": [
    {
      "id": "support-queue",
      "label": "Support Queue",
      "path": "/apps/:appId/support-queue",
      "component": "SupportQueuePage",
      "requiresAuth": true,
      "purpose": "Full-page operator view of the support request queue."
    }
  ]
}
```

**Example — `admin/pages/SupportQueuePage.jsx` (React page):**

```jsx
import { WorkspaceLayout } from '@mozaiks/chat-ui/workspace';

export default function SupportQueuePage() {
  return (
    <WorkspaceLayout>
      {/* operator content */}
    </WorkspaceLayout>
  );
}
```

**Example — `admin/index.js` (registration barrel):**

```js
import SupportQueuePage from './pages/SupportQueuePage.jsx';

export function register(registerComponent) {
  registerComponent('SupportQueuePage', SupportQueuePage);
}
```

## Choosing the Right Tier

| Condition | Tier |
|---|---|
| Module-owned entity data (records, metrics, queues, audit feeds) | **Tier 1** |
| Standard primitives (DataTable, Form, SummaryStrip) are sufficient | **Tier 1** |
| Surface must render inside the unified admin shell | **Tier 1** |
| AppGenerator is producing a standard generated app | **Tier 1** |
| Full-page layout with custom workspace chrome is required | **Tier 2** |
| Panel primitive system cannot express the operator surface | **Tier 2** |

When in doubt, use Tier 1. Tier 2 is an explicit escape hatch, not the default.

---

## Common Mistakes

| Mistake | Correct approach |
|---|---|
| Adding `component` / `registry_key` to `admin/admin_registry.yaml` | Use `ui/route_manifest.json` for full-page routes |
| Using `PageFrame` in `admin/pages/*.jsx` | Use `WorkspaceLayout` |
| Route_manifest entry without `admin/index.js` registration | All three files required together |
| Tier 2 page declared in `manifest.pages` or as a user-facing route | Admin operator pages go in `admin/pages/`, not `ui/pages/custom/` |
| Tier 1 panel referencing a page id not in `admin_registry.yaml` | Run the admin registry quality gate before download |
